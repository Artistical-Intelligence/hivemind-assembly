# ChatGPT Chat Mode multi-session scheduling audit — November 4, 2026

**Evidence status: registry-verified within named, bounded tests; HA application remains CHECKS PENDING.** This reviews multiple *scheduled executions in other ChatGPT conversations*, not simulated model output. Actual Automations task records and their latest-result IDs were reread by exact ID. When an author's result says `in_progress`, a later completed registry entry with matching run ID is authoritative. Historical records are available only to the extent preserved in completed result text; `peek` typically exposes only the latest run.

**Scope:** ChatGPT Chat Mode scheduling experiments only. No testing here grants permission for Claude, Work, Codex, other MCP tools, model/effort switching, a native HA scheduler, or automatic independent acceptance. No private RE-Wizard files or schedules were changed by this HA audit.

**Timing observation:** Service starts varied by minutes before/after `scheduled_for`; self-reports written while running often say `in_progress` even though a later registry read records completion. Prefer `last_run.id` matched to `latest_result.run_id`, completed timestamps and exact persisted prompt/schedule. Do not promise precision from a VEVENT.

**Task-identity lifecycle:** The one-off used in the initial parent-child and necromancy tests was later *reassigned as a substantive RE-Wizard CI worker*. The permanent task ID was retained while its current prompt, title, recurrence, project role and latest run changed. An orchestrator must verify *current* ownership and mutable assignment/revision before changing a task; archive earlier completed run receipts externally instead of assuming `peek` retains a full history. Do **not** touch the now-active private worker to repeat an old experiment.

## 2. Real-work evidence (privacy-limited case study)

The separate private BinaryWorkbench team provided an important non-synthetic check of scheduling and handoff behavior. Multiple specialized workers recorded **overlapping actual completed run intervals**, distinct ChatGPT chat refs and independently persisted source changes. A later integrator and provisional verifier consumed exact prior artifacts for static reviews. Later still, the shift manager identified a failing composite synthetic test run, **reassigned an existing authorized worker using a corrective brief**, and a subsequent completed worker execution consumed the failure evidence and committed substantive corrective work. This is **a real end-to-end corrective handoff**, not merely prompt update.

Private CI now runs genuine source-bound synthetic tests and exposes real failures. A recorded expanded composite run had **376 total: 360 passed, 6 failed, 10 skipped**; another later run had **443 total: 432 passed, 10 failed, 1 errored, 0 skipped**. Different revision sets, dependency provisioning, and test selections prevent direct score comparisons. The newer run remains a failed CI gate and does **not** establish integration or qualified reviewer acceptance. Other active workers' revisions are changing; avoid copying private file/task IDs, protected source or sensitive metadata into this public HA record. The [case study](REWIZARD_BINARYWORKBENCH_CASE_STUDY.md) retains the abstracted observations.

**Shift-manager evidence boundary:** A corrected assignment and later receiving run have been verified in the real workload. It has **not** demonstrated that every corrective assignment gets an earlier-than-normal dispatch, that a single-event corrective task can run inside one hour of a previous invocation, or that the manager's current phase mathematically maximizes its own preparation runway. Those remain open, despite the successful task-reuse proof.

HA's `chat_mode_profile.py` is conditionally appended only for the explicitly configured OpenAI Chat route; a file in GitHub is not automatically loaded by every scheduled task. The scheduling reference `SKILL.md` is committed but is not an installed ChatGPT skill.

## 4. Required changes to HA methodology

- **Keep a capability matrix with evidence tiers:** supported in service, accepted configuration, completed execution, correct artifact, qualified independent review and HA-native implementation are separate.
- **Use an advance-provisioned, safely scoped workforce:** existing scheduled tasks can be retasked, paused, re-enabled, or resurrected; do not infer unlimited creation or a supported scheduled-run child spawn.
- **Parallel and inherited waves both matter:** tasks must be genuinely separate work, and an inherited correction must reference exact source/test evidence. A real manager correction has been observed, but the broad reusable policy still needs independent application tests.
- **Do not make the shift manager a prerequisite for unrelated work.** Choose its hourly phase to maximize its own useful runway after the *relevant* work is ready, using observed completion times/jitter, not a fixed inherited phase. No guarantee that every asynchronous role is finished at the same instant.
- **Corrective *one-time* assignments are semantically distinct from repeated `RRULE` work:** the hourly recurrence rule does not by itself establish a per-ID cooldown for separately completed one-time assignments. The two-revival proof did not test earliest possible sub-hour restart. Request and verify the earliest actually allowed future event; do not manufacture copies to defeat service limits.
- **Protect source and reviews:** no game testing, copyrighted asset execution, unauthorized whole-textbook access, unreviewed main merge, prompt-only model/effort switches or mutable shared-file races.
- **Keep instructions light and actionable:** deeper scheduled invocations, compact revision-bound handoffs, early experimentation to unblock cross-lane test paths, and meaningful owner milestone updates. No sprawling per-run performance ledger or repetitive speculative probes.
- **Current task IDs are mutable ownership:** a test-owned one-off can become a production worker. Never touch or revive it solely because an old evidence record still contains its ID. Respect the latest owner-assigned task key, pause reason, source permissions and schedule.
