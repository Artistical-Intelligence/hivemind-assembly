## Why this case is useful

Unlike the isolated November 3–4 automation probes, this is ongoing substantive work to improve an automated, non-AI decompilation/recompilation program. The owner explicitly requested that HA's orchestration methodology be informed by whether **multiple workers operate concurrently and whether their verified outputs flow to later waves**. HA itself targets ChatGPT and Claude, but these Chat Mode scheduling experiments are **exclusive to ChatGPT**, not evidence that Claude, Work or Codex have the same capabilities.

### Workforce and intended interleaving

The private project has **five explicitly pre-provisioned Chat Mode scheduled roles**: compiler-metadata/identification worker, pipeline/recompilation reliability worker, provisional verifier, integrator, and conductor. These are distinct work responsibilities, not five model-qualified independent conversations. The conductor is the sole automation-assignment and timing editor; workers own nonoverlapping branches/output paths; acceptance and final integration remain separate. No game tests or untrusted compiler execution are authorized. Each worker uses a shared durable final goal, a role-specific current milestone, and an external project checkpoint.

The target pattern combines both:

- **Parallel:** two technical workers can make different useful changes at once; verification may examine prior completed output while unrelated implementation continues; the integrator need not hold unrelated work.
- **Inherited/serial waves:** source discoveries, a compiler manifest result, a failed synthetic test, a verifier finding or integration conflict can become the **next scoped assignment** for the same worker or a pre-existing colleague. Use exact artifact revision/commit lineage, not an assumed shared chat transcript.
- **Adaptive control:** conductor reviews actual work and changes existing roles' prompts, DTSTART/RRULE, enabled status and assignments **when permitted**. Staggered planned start times do not prove actual overlap. Multiple run IDs may share a chat ref, so a verifier's separate task ID is not automatically qualified independent review.

## Deep work per scheduled invocation (owner update, November 4)

The owner wants **substantially more productive individual executions**. A
worker should continue through **multiple feasible implementation and
targeted testing steps within a single scheduled run** instead of stopping at
its first committed edit, finished issue, short report, or checkpoint. A commit
is a durable recovery boundary, not a natural finish line. After each useful
change, continue the same coherent task, run available safe synthetic
regressions, fix newly discovered defects, and pick up another worthwhile
nonconflicting step when resources permit. Checkpoints remain mandatory for
recovery, revision provenance and independent review; workers must **not**
treat them as work quotas.

The actual private scheduled workforce now has this rule in its **saved task
prompts**, including its conductor, technical workers, verifier, integrator,
and milestone reporter. That is verified prompt state, **not proof** of
longer-running or more productive future model executions. Real service
runtime, context, tool approval, model usage and other limits are not under
task instruction control, and an hour-long execution cannot be guaranteed.
Do not try child/duplicate/run-now wakeup loops to extend a run.

For the live review, look at each worker's **completed run and actual
revisioned artifacts**: did it proceed beyond one initial commit or report
into additional useful code, targeted synthetic tests, diagnosis, correction
or verification when possible? Were later tasks blocked by concrete limits?
Evaluate substance and genuine tested outcomes, **not** mere elapsed
minutes, number of commits or another operational performance ledger. Use
confirmed GitHub source/commit/test evidence, preserving project privacy.
Avoid criticizing a run for ending at a genuine service/runtime boundary.

## Known failures and prevention — owner retrospective, November 4

The owner identified three concrete weaknesses in the live, real-work
orchestration, distinct from the earlier synthetic scheduling tests:

- **Wrong execution boundary:** Workers could use authenticated GitHub
  connected tools but could not obtain a normal private checkout in
  their own execution environment. Some direct network requests also
  suffered DNS failures. They treated these route-specific limitations
  as if **all source-bound tests** were unavailable.
- **Speculation rather than experiment:** The integrator examined
  GitHub Actions configurations and permissions but did not conduct
  the decisive isolated minimal CI experiment. The owner supplied
  that empirical step, after which **multiple branch-isolated synthetic
  Actions runs succeeded**. They are real run successes for their
  specific test commits, not proof of current worker or integrated
  source HEADs passing the entire suite.
- **Shared blocker without ownership:** Separate code branches and
  exclusive editors prevented merge conflicts but masked an essential
  cross-team prerequisite. The conductor should have recognized the
  repeated test-execution gap and explicitly assigned an existing
  role to prove an alternative. The active interactive ChatGPT worker
  also had an opportunity to intervene earlier.

**Required prevention in future Chat Mode waves:** When a local clone
fails, do not report simply "tests cannot run." Build a small execution
route matrix and conduct an authorized **minimal real CI probe** on
an isolated safe branch before another research-only report; inspect
the actual run/commit and any approval denial. When two workers
report the same blocker or it repeats for two completed waves, the
conductor must designate an accountable worker/integrator to resolve
that shared prerequisite while unrelated implementation continues.
Preserve ownership for **writes**, not for recognizing and raising
a cross-team problem. The main interactive chat contributes useful
experiments during its active turns. One scoped passing Actions
workflow still requires current-revision binding, correct test
selection, exact pass/fail/skip accounting, integrated checks, and
qualified independent review before acceptance.

## Evidence collection rules

For each later bounded observation:

1. Inspect unique exact task identities and `recorded_status`, `scheduled_for`, `started_at`, `completed_at`, `latest_result.run_id`, `chat_ref`, and any current prompt/schedule changes. A null `next_run_time` is not proof that an enabled recurrence cannot run.
2. Verify any claimed GitHub work against actual private repository branch/PR metadata **with authorized read tools**. Never disclose private source text, filenames outside already approved public references, account IDs, secrets, protected inputs, or full artifacts here. Never write to the active private project or take over its conductor.
3. To claim **actual concurrent execution**, find at least two overlapping start/finish intervals for different tasks, and note whether tools/model sessions and writers were genuinely separate; merely staggered planned hours do not prove it.
4. To claim **inheritance**, find a completed producing wave with an exact committed artifact SHA, a subsequent receiving task consuming that exact revision/finding, and its own completed result. Prompt updates alone prove reassignment, not successful consumption of results.
5. Classify verifier findings as **provisional** unless independently qualified context/model and required review boundaries are verified; a separate task ID, separate branch or even a different chat ID by itself is insufficient.
6. Keep findings concise and evidence-only. No performance ledger or duplicate full-run transcripts. On each material new test result, update the [Chat Mode findings](CHAT_MODE_FINDINGS.md), this case study, and, if a capability/limitation changes the reusable procedure, the [skill](../../skills/chatmode-scheduled-orchestration/SKILL.md) / [conductor policy](CONDUCTOR.md), preserving CHECKS PENDING and provider scope.
